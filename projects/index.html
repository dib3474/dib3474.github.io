FestaPick | 축제 추천 및 실시간 소통 플랫폼

2025년 8~11월 카카오테크캠퍼스 3기에서 6인 팀으로 진행했습니다. 프론트엔드 설계와 구현을 맡았습니다.

문제

축제를 고르는 사람은 일정과 장소를 확인한 뒤에도 어떤 행사가 자신의 취향에 맞을지 고민합니다. 특히 처음 가는 축제는 공식 안내만으로 현장 분위기를 가늠하거나 방문 전에 생긴 궁금증을 풀기 어렵습니다.

맡은 역할

컴포넌트 구조

페이지 전용 요소와 공통 요소를 분리하고 리뷰 이미지 모달은 여러 화면에서 재사용할 수 있도록 공통 컴포넌트로 옮겼습니다. 화면에서 쓰는 상수도 별도로 분리해 수정 위치를 쉽게 찾도록 했습니다.

화면 테스트

버튼 클릭과 비활성 상태에서의 동작을 단위 테스트로 확인했습니다. 축제 상세 화면의 포스터 이미지와 이전 및 다음 버튼을 스냅샷 3개로 기록해 변경점을 비교할 수 있게 했습니다.

API 연동

응답 형식이 기능마다 달라 화면별 처리가 필요했습니다. 백엔드 팀과 일반 조회, 무한 스크롤 조회, 작성 API의 응답 구조와 필드 이름을 조율하고 공통 오류 처리 함수와 로딩 및 오류 화면을 구현했습니다.

실시간 채팅

채팅방을 오갈 때 WebSocket 연결을 공유하도록 React Context에서 관리했습니다. 같은 채팅방의 STOMP 구독은 재사용하고 방을 나갈 때 해당 구독을 해제하도록 정리했습니다.

기술

React, TypeScript, TanStack Query, Tailwind CSS, WebSocket(STOMP), Vitest, Testing Library, MSW

결과

축제 탐색을 이어갈 수 있게 개선

축제 상세 화면을 보고 돌아왔을 때 캐시에 저장한 이전 추천 결과를 다시 표시했습니다. 참여자는 성향을 다시 입력하거나 추천을 다시 실행하지 않고 같은 목록에서 다른 축제를 비교할 수 있게 됐습니다.

이미지 보기와 오류 안내를 공통화

축제 상세의 리뷰, 축제 공지, 내가 작성한 리뷰에서 같은 이미지 모달을 사용했습니다. 이미지 보기 동작을 바꿀 때 세 곳의 화면을 각각 수정하는 대신 공통 컴포넌트 한 곳을 수정하면 됩니다. API 요청이 실패하면 공통 오류 처리 함수에서 네트워크 오류나 서버 응답에 맞는 메시지를 정해 여러 화면에서 같은 기준으로 안내할 수 있게 했습니다.

화면 변경을 확인할 기준 마련

축제 상세의 포스터 이미지와 이전 및 다음 버튼을 각각 스냅샷으로 기록했습니다. 화면을 수정한 뒤 세 항목 중 어떤 요소의 렌더링이 달라졌는지 테스트에서 확인할 수 있게 됐습니다.

재연결 뒤 채팅 수신 복구

같은 채팅방에 대한 구독 요청이 여러 번 들어와도 기존 STOMP 구독을 재사용하도록 구현했습니다. 연결이 끊겼다가 다시 연결되면 참여 중인 채팅방을 다시 구독해 이후 올라오는 메시지를 받을 수 있게 했습니다.

후속 개선

팀 프로젝트가 끝난 뒤 개인 포크에서 모바일 접근성과 초기 로딩을 개선하고 변경 전후를 측정했습니다.

접근성

공통 모달의 초점 처리와 추천 화면의 키보드 조작을 개선했습니다. 동일한 샘플 데이터와 375px 화면에서 Lighthouse 접근성을 자동 진단했습니다. 검색 화면은 82점에서 100점으로 올랐고 축제 상세 화면은 78점에서 100점으로 올랐습니다. 전체 8개 화면의 결과는 모바일 UI 개선 PR에 정리했습니다.

초기 로딩

일부 페이지와 채팅 라이브러리를 필요할 때 불러오도록 변경했습니다. 별도 로컬 실험에서 390px 화면을 경로별로 변경 전후 각각 5회 측정해 중앙값을 비교했습니다. 홈과 축제 목록 및 상세의 첫 진입에 전송된 JavaScript는 197.0 KiB에서 159.6 KiB로 19.0% 줄었습니다. 축제 상세의 주요 콘텐츠 표시 시간(LCP)은 2.25초에서 6.98초로 늘어 포스터 로딩을 후속 개선 과제로 남겼습니다.

  • 기능별 시연 화면
  • 프론트엔드 소스 코드
  • 채팅 구독 코드
  • 축제 상세 테스트

CrewMate | 건설 일용직 인력 중개 플랫폼

2026년 7월 부산대학교 클라우드 AI PBL에서 3인 팀으로 진행했습니다. AI가 추천한 건설 인력 조합을 실제로 배정할 수 있는지 검증하는 기능과 보고서에 쓰이는 검색 자료 구축 및 인용 검증을 맡았습니다.

문제

건설사에서 인력을 요청하면 인력사무소는 전화와 종이 기록을 확인해 요청한 날짜에 일할 수 있는 근로자를 찾았습니다. 일할 수 있다는 답을 받아도 직종별 인원이 맞는지와 임금 합계가 예산을 넘지 않는지를 따로 확인해야 했습니다.

근로자가 희망 직종을 준비할 때는 필요한 자격과 보완할 역량을 파악하기 위해 큐넷과 국가직무능력표준 자료를 따로 확인해야 했습니다.

맡은 역할

검색용 데이터 구축

건설 직종의 자격과 역량 요건을 공공데이터에서 수집하고 자격증 명칭을 정리했습니다. 각 문서에 직종, 자격증 명칭, 원본 출처를 담아 보고서가 해당 직종에 맞는 근거를 찾을 수 있도록 구성했습니다. 검색 자료를 Amazon Bedrock Knowledge Bases에 적재하는 과정도 작성했습니다.

인력 추천 검증

AI가 추천한 근로자를 데이터베이스의 후보 목록과 대조했습니다. 근로자의 배정 가능 상태와 중복 여부를 확인하고 요청한 직종별 인원과 예산도 검사하도록 구현했습니다.

보고서 인용 검증

보고서가 인용한 문서와 링크를 Bedrock 검색 결과 및 큐넷(Q-Net) 조회 결과와 대조했습니다. 검색에서 반환된 문서 ID를 다른 ID로 바꿨을 때 검증이 실패하는 테스트를 추가했습니다.

기술

Python, Strands Agents, Amazon Bedrock Knowledge Bases, Amazon S3 Vectors, DynamoDB, pytest

결과

실제 배정 조건에 맞는 추천안 검토

후보 목록에 없거나 현재 배정할 수 없는 근로자가 포함된 추천안과 같은 근로자가 중복된 추천안을 검증 단계에서 걸러냈습니다. 예산만 초과한 추천안은 초과 금액을 표시해 인력사무소가 임금을 조정한 뒤 승인할 수 있게 했습니다.

직종별 근거를 검색할 수 있게 정리

직종별 자격 요건과 역량 요건을 포함한 검색 자료를 CSV 4종으로 정리했습니다. 저장소에 기록된 문서 ID는 중복 없이 총 655개입니다. 보고서가 희망 직종에 해당하는 요건을 찾을 수 있도록 직종별로 검색 범위를 좁혔습니다.

조회 결과에 있는 출처를 보고서에 사용

조회한 자료에 없는 문서를 보고서가 인용하면 검증 오류로 처리했습니다. 재현 테스트에서 검색 결과에 없던 문서 ID가 검증을 통과하지 않는지 확인할 수 있게 했습니다. 근로자는 보고서에 표시된 큐넷 링크에서 자격 정보를 직접 확인할 수 있습니다.

근거 조회를 출처별로 묶어 처리

프로젝트를 진행하면서 보고서의 요건마다 도구를 호출하던 흐름을 바꿨습니다. Bedrock 검색과 큐넷 조회 요청을 출처별로 묶어 보고서 생성 시도마다 각 도구를 최대 한 번 호출하도록 했습니다. 도구 안에서는 개별 조회를 병렬로 처리했습니다.
